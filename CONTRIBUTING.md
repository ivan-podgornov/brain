# Инструкции для разработки

## Цель проекта

Цель проекта - улучшить свои навыки программирования. Мне не нужен работающий проект (хотя это
было бы огромным плюсом), мне нужно лучше разобраться в таких концепциях как: проектирование
архитектуры приложений, паттерны проектирования, инверсия зависимостей, разделение ответственности,
тестирование. Отсюда должны исходить все решения.

## Развернуть проект

Чтобы развернуть проект, нужно склонировать этот репозиторий, зайти в папку с проектом и выполнить
`npm install`. Всё, на этом проект считается готовым к разработке.

## Архитектура

Приложение разделено на три слоя:

- **toolkit** - утилиты, которые не зависят от бизнес-логики и могут использоваться в любой другой
  игре без изменений. Сюда можно отнести HTN, систему поиска маршрута по графу, event emitter.
- **core** - бизнес-логика, актуальная конкретно для этого мира. Сущности по типу world, npc, car.
  При этом сущности должны быть максимально независимыми друг от друга. Например, NPC не должен
  ничего знать о мире. Если ему нужно подписаться на тики, мир должен в конструкторе передать
  событие на которое можно подписаться и которое будет вызываться каждый тик. Но не должно быть
  такого, что NPC подписывается на мир.
- **mod** - Мод - это слой, который реализует сущности из core и заставляет их работать в игре.

Слой более нижнего уровня не должен знать о слоях выше.

## Тестирование

### Принципы

1. Тесты должны быть спецификацией проекта. Не должны использоваться формулировки тест-кейсов,
   которые не отражают причинно-следственные связи. Тест-кейсы пишутся в формате утверждений:
   "_возвращает_", "_вызывает_", "_выбрасывает_". Приветствуется использование шаблонных фраз:
   "если _условие_, _утверждение_". Если какой-то набор тест-кейсов повторяется при определённом
   состоянии, это состояние может быть обёрнуто в отдельный `describe`, который именуется по шаблону:
   "_При_ таком-то состоянии".
2. На один тест должна приходиться одна-две проверки.
3. Избегаем happy path тестов. Лучше несколько атомарных тестов, чем один happy path
4. Придерживаемся принципа **A**rrange, **A**ct, **A**ssert.
5. Все данные для теста формируются в самом тесте. Не используем
   beforeAll, beforeEach, afterAll, afterEach - они усложняют понимание одного конкретного теста.
6. Значимые для теста моки, описываются в самом тесте. Незначимые, при необходимости, выносятся
   в отдельную константу и могут переиспользоваться между тестами. Главное, чтобы они создавались
   всегда новые для каждого теста. Например, если тест проверяет, что при определённом уровне голода
   NPC падает в обморок, npc должен быть создан в тесте, голод должен фигурировать в тесте, а все
   остальные данные, например, такие как жажда, бодрость могут быть указаны в константе.
7. В одном файле должна проверяться только одна фича. Если проверок сильно много, файл разделяется
   на подфайлы в которых проверяются подфичи или разбивается на проверки при определённых событиях.
